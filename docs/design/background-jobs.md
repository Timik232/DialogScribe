# Фоновая обработка: почему «телефон выключился → расшифровка пропала» и что делать

Статус: предложение (не реализовано). Дата: 2026-10-17.

## Диагноз (по коду, не по ощущениям)

В проекте два долгих сценария, и оба **привязаны к живому соединению клиента**:

### 1. Основной флоу — `POST /api/transcribe` (routers/transcription.py)

- Вся транскрипция выполняется **внутри HTTP-запроса**: `asyncio.to_thread(_transcribe_upload, ...)`.
- Результат существует только в HTTP-ответе. Сохранение (`POST /api/saved-transcriptions`) —
  отдельный вызов, который делает **клиент после получения ответа**.
- Телефон гаснет / браузер сворачивается → ОС убивает сокет (iOS ~30 сек в фоне,
  Android Doze) → ответ доставить некуда. Сервер либо докручивает работу вхолостую,
  либо соединение рвётся раньше. В обоих случаях **результат потерян для пользователя**,
  потому что на сервере его никто не сохранил.
- Долгие файлы дополнительно рискуют упереться в таймауты proxy-цепочки
  (DSM reverse proxy на .47 → ingress-guard). В ingress-guard стоит
  `proxy_read_timeout 3600s`, но настройки vhost в DSM не проверялись —
  дефолт nginx 60s молча убил бы «тихий» (без байт в ответ) длинный POST.

### 2. Autoflow — `WS /api/autoflow/ws` (routers/autoflow.py)

- Здесь хуже: `watch_controls()` на `WebSocketDisconnect` делает `cancelled.set()`
  → `work_task.cancel()` — то есть **отключение клиента активно убивает обработку**.
- `finally`-блок удаляет загруженный tempfile. Результат autoflow вообще
  не персистится (нет ни записи в БД, ни авто-save).
- Никакого reconnect/resume протокол не предусматривает (session_id выдаётся,
  но повторно подключиться к сессии нельзя).

### 3. Мелкие усугубители

- `transcriptionStore` живёт в **sessionStorage** (frontend/src/lib/stores/transcription.ts) —
  закрыл таб → даже готовый прошлый результат исчез.
- Wake Lock API не используется; `visibilitychange` не обрабатывается.
- Инфраструктуры фоновых задач нет вообще: ни таблицы заданий, ни очереди, ни polling API.

**Вывод:** это не баг соединения, это архитектурный дефект — durable-работа
выполняется в рамках ephemeral-соединения. На мобильных ОС сохранить сокет
живым при погасшем экране невозможно в принципе, значит чинить надо не сокет.

## Предложение: серверные jobs + polling + автосохранение

### Фаза 1 — ядро: job-модель для транскрипции

1. Таблица `transcription_jobs` (миграция alembic, следующая после 009):
   `id uuid PK, user_id FK, status (queued|processing|completed|failed|cancelled),
   stage, progress, params JSON (diarization/language/denoise/provider),
   input_path (durable-том, не auto-delete tempfile),
   result JSON / error, created_at/updated_at/started_at/finished_at`.
2. API:
   - `POST /api/jobs` (multipart) — быстрая фаза: создать job + принять файл, вернуть `{job_id}`;
   - `GET /api/jobs` — список «моих обработок» (активные + история);
   - `GET /api/jobs/{id}` — статус и результат (для `completed`);
   - `DELETE /api/jobs/{id}` — отмена.
3. Обработка — asyncio-таска в процессе (MVP), стартует после создания job.
   Postgres-строка — источник истины: рестарт контейнера → startup-sweep
   помечает осиротевшие `processing` как `failed` (паттерн sweep уже есть:
   `sweep_stale_tempfiles`). Бонус: семафор/очередь защищает GPU от N параллельных пользователей.
4. **Автосохранение результата** в `saved_transcriptions` на сервере при завершении job.
   Результат становится durable независимо от того, жив ли клиент. /transcriptions
   превращается в полную историю.
5. Фронт: после upload поллинг `GET /api/jobs/{id}` раз в 3–5 c с backoff;
   `visibilitychange` → немедленный re-poll при возврате в таб.
   Погас экран → работа на сервере продолжается; открыл заново → увидел результат.

**Почему polling, а не WS/SSE:** каждый poll — короткий запрос, который проходит
через любой proxy с любыми idle-таймаутами; переживает перезагрузку страницы и
таба; тривиально восстанавливается. WS/SSE — ровно то, что умирает на мобильном
фоне (см. autoflow). WS остаётся для live-hints (там это оправдано).

### Фаза 2 — устойчивость существующих флоу

- Autoflow: разделить «транспорт умер» и «пользователь нажал cancel».
  Transport-disconnect → работа продолжается до конца и персистится (job-строка);
  явный `{"type":"cancel"}` → отмена. Reconnect по `session_id` → переподключение
  к прогрессу/результату. В идеале autoflow UI переезжает на тот же job-API
  (upload через HTTP, WS — только опциональные live-прогрессы).
- Старый `POST /api/transcribe` оставить как есть (API-совместимость, /v1-поверхность),
  UI переводится на jobs. Как минимум — quick-win: серверное автосохранение результата
  и в этом эндпоинте, чтобы «ответ потерялся, но расшифровка в истории».

### Фаза 3 — мобильный UX

- Экран «Обработки»: активные job с прогрессом, история (фактически = /transcriptions
  после автосохранения).
- Email-уведомление о завершении: SMTP уже настроен (aiosmtplib, smtp.mail.ru) —
  «Расшифровка готова» + ссылка. Дёшево и закрывает сценарий «ушёл с телефона».
- Опционально PWA + Web Push (iOS 16.4+ для установленных PWA, Android — да).
- Wake Lock — только на фазу загрузки файла (и то опционально): с jobs он больше не нужен
  для обработки.
- Отдельная тема (не блокер): resumable-upload (tus) для 1 ГБ файлов по мобильному
  интернету — jobs чинят потерю *обработки*, но не потерю *загрузки*.

### Quick-wins (можно сделать до/вместе с фазой 1, каждое — мелкий PR)

1. `sessionStorage` → `localStorage` в transcriptionStore (1 строка + версия схемы).
2. Autoflow: не отменять работу при disconnect (несколько строк в watch_controls).
3. Серверное автосохранение результата `/api/transcribe` (один insert + тест).
4. Проверить/поднять `proxy_read_timeout` vhost в DSM (диагностика: 504 в логах RP).
